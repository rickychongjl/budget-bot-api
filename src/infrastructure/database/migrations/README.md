# Migrations

Generated by `npm run db:generate` from `src/infrastructure/database/schema/*.ts`.
**Forward-only — no
down migrations** (M1 §5). The committed SQL is the source of truth.

M1 owns no tables itself. `0000_identity.sql` carries M2's `app_user` /
`channel_connection`; `0001`/`0002` add M8's and M6/M9's tables; `0003` is the single
coordinated M3+M4 migration carrying their cross-FK tables (`category` ↔ `budget`,
`transaction` ↔ `budget_period`) — see master plan §4. `transaction.category_name_snapshot`
was proposed in M3's plan for the deferred "real category removal" feature and
deliberately **not** included (confirmed 8 Sep); it arrives with the feature that
needs it. `0007` is M4's cap history (`category_period_cap`, 12 Sep): the one
migration here that **moves data** — its three backfill `INSERT`s are hand-written
between drizzle-kit's `CREATE` and `DROP COLUMN` statements, and
`test/integration/migration-0007-category-period-cap.test.ts` pins what they do to
old-shape rows.

Flow:
1. A module edits its own `src/infrastructure/database/schema/<module>.ts` and the
   barrel `index.ts`.
2. `npm run db:generate` writes `NNNN_<name>.sql` + `meta/` here; commit both.
3. CI applies these to a throwaway Neon branch per PR (`npm run db:migrate`).
4. On merge to `main`, the deploy job runs `db:migrate` against production and must
   succeed before `wrangler deploy`.
